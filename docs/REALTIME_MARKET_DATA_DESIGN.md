# 实时行情与联动架构：需求、架构设计与注意要点

本文档基于前期讨论结论，对「守护程序事件驱动 + Redis 缓存 + 监控端联动」的调整方案做**需求、架构设计、注意要点**的成文定义，作为实现与评审的单一参考。与 [ARCHITECTURE.md](ARCHITECTURE.md) 和 [REQUIREMENTS.md](REQUIREMENTS.md) 保持一致；涉及新增组件（Redis、联动通道）时以本文为准。

---

## 1. 需求（需求）

### 1.1 守护程序双线运行

| 编号 | 需求描述 | 说明 |
|------|----------|------|
| R-RM1 | 守护程序同时维护**心跳循环**与**事件订阅**两条线。 | 心跳循环：定时写状态/心跳到 PostgreSQL、轮询 `daemon_control` / `daemon_run_status`。事件订阅：在 IB 回调中处理 tick/持仓/订单，更新内存状态；两条线可共用同一 asyncio 事件循环，不得互相阻塞。 |
| R-RM2 | 行情与持仓的更新以 **IB 事件驱动** 为主，不以轮询为主。 | 使用 `reqMktData` / `reqPositions` / 订单回报等回调作为数据源；轮询仅用于控制通道（读 DB 指令）。 |

### 1.2 实时行情缓存与唯一写入方

| 编号 | 需求描述 | 说明 |
|------|----------|------|
| R-RM3 | 事件订阅得到的**市场行情**写入 **Redis**，作为低延迟缓存。 | 目的：高频 tick 不直接写 PostgreSQL，避免成为瓶颈；监控/API 或前端需要「当前价」时从 Redis 读取。 |
| R-RM4 | Redis 中行情数据的**唯一写入方为守护进程**。 | 监控 Server **不得**向 Redis 写入市场行情；监控仅通过「联动机制」消费守护发出的通知并读 Redis（或使用消息体），再推给前端。 |

### 1.3 联动机制（守护 → 监控）

| 编号 | 需求描述 | 说明 |
|------|----------|------|
| R-RM5 | 守护进程在写入 Redis 行情后，通过**联动通道**通知监控端「有更新」。 | 监控端无需轮询 Redis；事件驱动地获知更新，再读 Redis 或解析消息体，向已连接的前端推送。 |
| R-RM6 | 联动通道采用 **Redis Pub/Sub** 或 **Redis Streams**，不引入额外中间件。 | 守护进程不直接连接监控 Server 的 IP/端口；监控与守护仅需能访问同一 Redis 实例。 |

### 1.4 监控端职责边界

| 编号 | 需求描述 | 说明 |
|------|----------|------|
| R-RM7 | 监控 Server **订阅**联动通道；收到通知后**读取 Redis**（或使用消息内数据）并推送给前端。 | 可选实现：WebSocket 或 SSE；前端亦可短轮询 `GET /quotes`（监控从 Redis 读后返回）。 |
| R-RM8 | 监控 Server **不**向 Redis 写入市场行情。 | 避免双写、职责不清与数据源冲突。 |

### 1.5 何时在 UI 提供实时行情

| 场景 | 是否需要在 UI 获得实时市场数据 | 说明 |
|------|------------------------------|------|
| 操作中监控、与守护行为对照、同屏做手工决策、建议模式下的体验 | **需要** | 通过 Redis 缓存 + 联动 + 前端推送（或轮询）实现。 |
| 仅健康检查、事后复盘、只看建议序列与统计、非交易时段 | **不需要** | 定期刷新 status、历史数据与 operations 即可。 |

### 1.6 可选：建议模式先行（第一里程碑）

| 编号 | 需求描述 | 说明 |
|------|----------|------|
| R-RM9 | （可选）第一里程碑为**仅建议、不真实下单**：守护进程完整跑 StateClassifier + FSM + Guard，但在执行层截断，将 hedge intent 写入 operations（如 `type=hedge_recommendation`），由 Web UI 呈现。 | 便于先验证策略与风控逻辑，再开放实盘。 |

## 2. 架构设计（架构设计）

### 2.1 总体数据流

```
                    ┌─────────────┐
                    │    TWS      │
                    └──────┬──────┘
                           │ 事件推送（tick/持仓/订单）
                           ▼
┌──────────────────────────────────────────────────────────────────────────┐
│  守护进程 (run_engine.py)                                                  │
│  ┌─────────────────┐    ┌─────────────────┐                             │
│  │ 心跳循环         │    │ 事件订阅（IB）   │                             │
│  │ · 写 PG 状态     │    │ · 更新内存       │                             │
│  │ · 轮询控制       │    │ · 写 Redis 行情  │ ──► Redis (SET/HSET)        │
│  └─────────────────┘    │ · 发布联动通知   │ ──► Redis (PUBLISH / XADD)  │
│                          └─────────────────┘                             │
└──────────────────────────────────────────────────────────────────────────┘
       │                                            │
       │ 写 status_current / daemon_control 等      │ 写缓存 + 发通知
       ▼                                            ▼
┌─────────────────┐                        ┌─────────────────┐
│  PostgreSQL     │                        │  Redis           │
│  · 状态/控制    │                        │  · 行情缓存     │
│  · 操作/历史    │                        │  · Pub/Sub 或    │
└────────┬────────┘                        │    Streams       │
         │                                 └────────┬────────┘
         │ read                                     │ subscribe
         ▼                                          ▼
┌──────────────────────────────────────────────────────────────────────────┐
│  监控 Server (run_server.py)                                               │
│  · 读 PG → GET /status, /operations, 控制 POST                            │
│  · 订阅 Redis 联动通道 → 收到通知 → 读 Redis（或解析消息）→ 推给前端        │
│  · 不写 Redis 行情                                                         │
└──────────────────────────────────────────────────────────────────────────┘
         │
         ▼
┌─────────────────┐
│  前端 (Web UI)   │  ← WebSocket/SSE 或 轮询 GET /quotes
└─────────────────┘
```

### 2.2 组件职责表

| 组件 | 职责 | 写入 Redis | 读取 Redis | 联动通道 |
|------|------|------------|------------|----------|
| **守护进程** | 心跳循环；IB 事件订阅；更新内存；写 PG 状态/控制消费；**写行情到 Redis**；**发布联动通知** | 是（行情） | 否 | 发布端 |
| **Redis** | 存最新行情缓存；提供 Pub/Sub 或 Streams 作为联动通道 | — | — | 通道 |
| **监控 Server** | 读 PG 提供 REST；**订阅**联动通道；收到通知后**读 Redis** 并推前端；**不写**行情 | 否 | 是 | 订阅端 |
| **前端** | 通过监控 Server 的 WebSocket/SSE 或 GET /quotes 获取实时行情 | — | 经 API | — |

### 2.3 Redis 使用约定（建议）

| 用途 | 类型 | Key/Channel 示例 | 说明 |
|------|------|------------------|------|
| 行情缓存 | String / Hash | `quote:{symbol}` 或 `quotes` (Hash: symbol → JSON) | 守护进程 SET/HSET；建议设置 TTL（如 300s）防止脏数据残留。 |
| 联动通知 | Pub/Sub | Channel: `quotes` 或 `daemon:quotes` | 守护 PUBLISH symbol 或简短 JSON；监控 SUBSCRIBE。 |
| 或：联动通知 | Streams | Stream: `quote_stream` | 守护 XADD；监控 XREAD 阻塞读；适合需多消费者或回溯时使用。 |

**当前实现**（与代码一致）：行情缓存 key 为 `quote:{symbol}`（String，JSON 体含 symbol、bid、ask、last、ts）；TTL 默认 300 秒；Pub/Sub 频道为 `daemon:quotes`，消息体为 `{"symbol": "NVDA", "ts": 1234567890}`。监控端提供 `GET /quotes`（可选 query `symbols=NVDA,AAPL`；无参数时使用关注列表：status 标的 + 持仓 + wishlist），从 Redis 批量读取后返回 `{"quotes": [{...}]}`。配置：`config.config.yaml` 中 `redis.enabled: true`、`redis.host`、`redis.port`（默认 6379）、`redis.db`、`redis.password`（可选）、`redis.quote_ttl_sec`、`redis.channel`；未配置或 `enabled: false` 时守护与监控均不连 Redis，GET /quotes 返回空列表与提示。

### 2.4 与现有架构的关系

- **不替代** PostgreSQL 在状态、控制、操作、历史中的角色；Redis **仅**作为行情实时缓存与联动通道。
- 守护进程仍为**唯一**连接 TWS 并执行交易逻辑的进程；监控与守护**物理解耦**，通过 PG + Redis 与守护协作。
- 符合 [ARCHITECTURE.md](ARCHITECTURE.md) §2（运行环境与部署约束）及 RE-5（监控与守护分离）。

## 3. 注意要点（注意要点）

### 3.1 数据与一致性

| 要点 | 说明 |
|------|------|
| **Redis 仅作缓存** | 不替代 PG；不做唯一持久化源。控制、操作记录、历史仍以 PG 为准。 |
| **行情唯一写入方** | 仅守护进程写 Redis 行情；监控 Server 不得写，避免双写与源冲突。 |
| **延迟差异** | UI 上的「实时」与守护进程内存在一定延迟（Redis 写 + 联动 + 网络）；不承诺「同一 tick 同一时刻」。 |

### 3.2 部署与依赖

| 要点 | 说明 |
|------|------|
| **Redis 可达性** | 守护程序主机与监控机均需能访问**同一 Redis**（同机或局域网）。 |
| **可选部署** | Redis 可与 PG 同机或独立；需在配置中显式声明（如 `redis.url` 或 `redis.host/port`）。 |
| **推荐部署** | **与 PostgreSQL 同机**部署 Redis 通常最省事：守护与监控本就需访问 PG，同机 Redis 无需改网络；Redis 仅作行情缓存与 Pub/Sub，负载轻，与 PG 共享一台“数据机”即可。若 PG 在守护机或监控机上，Redis 也可同机或放在另一台双方都能访问的局域网主机。 |
| **无 Redis 时降级** | 未配置或不可用时，守护进程不写 Redis、不发布；监控端仅依赖 PG 与现有 GET /status 轮询，不破坏现有行为。 |

### 3.3 性能与容量

| 要点 | 说明 |
|------|------|
| **Key 设计与 TTL** | 建议每标的一个 key 或一个 Hash，并设置合理 TTL（如 5 分钟），避免长期残留。 |
| **推送节流** | 监控端向前端推送时，可对短时间内的多次更新做合并/节流（如 100ms 内只推一次），降低前端刷新频率。 |
| **订阅范围** | 守护进程仅对「策略相关」标的（如持仓 + wishlist）写 Redis 与发布，避免全市场刷量。 |

### 3.4 安全与边界

| 要点 | 说明 |
|------|------|
| **Redis 访问控制** | 若 Redis 在局域网内，建议设置密码与绑定地址；不暴露到公网。 |
| **联动消息内容** | Pub/Sub 消息可仅含 symbol 或最小 JSON（如 symbol + ts），监控再读 Redis 取完整行情，减少消息体积与敏感信息泄露。 |

### 3.5 实现顺序建议

1. 守护进程：在 IB tick 回调中增加「写 Redis + 发布」逻辑；配置中增加 Redis 连接与开关。  
2. 监控 Server：增加 Redis 订阅与「收到通知 → 读 Redis → 推前端」；可选先实现 GET /quotes（从 Redis 读）供前端轮询。  
3. 前端：增加行情展示（如行情墙 / ticker）；再视需要增加 WebSocket/SSE 以降低轮询频率。
